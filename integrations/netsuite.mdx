How Trackstar's normalized ERP resources map to Oracle NetSuite: authentication, the resources and operations we support, and the field-by-field mapping in both directions.

All access is over NetSuite's SuiteTalk REST API, with reads served through SuiteQL (NetSuite's SQL layer over the same records). Reads are synced on a configurable schedule; writes are made on demand.

## Authentication

Trackstar connects to NetSuite using OAuth 2.0 in a machine-to-machine flow. The customer consents once at install; steady-state access uses a certificate, with no stored password and no user session.

**Customer setup.** Create a NetSuite integration record (Setup, Integration, Manage Integrations) with OAuth 2.0, Authorization Code Grant, and Client Credentials enabled, then provide an **Account ID**, **Client ID** (Consumer Key), and **Client Secret** (Consumer Secret). The granted scope is `rest_webservices`.

**Install (one time).** Trackstar exchanges the authorization code for a short-lived bootstrap token, generates a keypair, and uploads a self-signed certificate to NetSuite mapped to the consenting entity and role. The bootstrap token and client secret are used only during install and then discarded. The durable secret is the certificate's private key.

**Steady state.** Trackstar mints short-lived access tokens with a JWT assertion signed by the private key (`PS256`), exchanged with the `client_credentials` grant. Tokens are cached and re-minted on expiry.

<Note>
No NetSuite password is stored or transmitted. Access runs through a role you define and a certificate you can revoke at any time in NetSuite, so you control exactly what the connection can reach.
</Note>

## Conventions

Behavior shared across every resource.

- **Custom fields.** Every record carries a `custom_fields` map holding all of the account's custom fields on that record, discovered automatically: `custentity_*` on customers, vendors, and employees; `custbody_*` on sales and purchase orders; `custitem_*` on items and inventory; `custrecord_*` on locations. On write, custom-field values pass through natively and are validated against the record's metadata catalog.
- **Addresses.** Read addresses are normalized to `full_name`, `company`, `address1` through `address3`, `city`, `state`, `postal_code`, `country`, and `phone_number` (a subset per resource). On write, address objects convert to NetSuite `shippingAddress` and `billingAddress`; a partial address falls back to the entity's default.
- **Names.** For people, `name` is `firstname` and `lastname`; for companies it is `companyname`. `is_individual` reflects NetSuite's `isperson` flag.
- **Dates.** Timestamps are returned as ISO 8601 (UTC). On write, date-only NetSuite fields (`tranDate`, `shipDate`, `dueDate`) take the date portion only.
- **Identifiers.** Every `id` is the NetSuite internal id, returned as a string.

## Read field mappings

How each normalized field is sourced from NetSuite. NetSuite names are as they appear in SuiteQL and the Records Browser.

### Customers

Source: Customer record, with billing and shipping from the customer's default address book entries.

| :--- | :--- |

## Write field mappings

How each field on a Trackstar write request lands on the NetSuite record.

### Create sales order

| Trackstar field | Required | NetSuite target |
| :--- | :---: | :--- |
| `customer_id` | Yes | `entity` |
| `line_items` | Yes | Line items: `item`, `quantity`, `rate` (from `unit_price`), `location` |
| `reference_id` | No | `externalId` |
| `order_number` | No | `tranId` |
| `order_date`, `expected_ship_date` | No | `tranDate`, `shipDate` (date only) |
| `location_id` | No | `location` |
| `ship_to_address`, `bill_to_address` | No | `shippingAddress`, `billingAddress` |
| `notes` | No | `memo` |
| `custom_fields` | No | `custbody_*` |

On multi-subsidiary accounts, the subsidiary is set automatically from the customer.

### Update sales order

| Trackstar field | Behavior |
| :--- | :--- |
| `customer_id` | Cannot be changed after create; a change is rejected |
| `order_number`, `order_date`, `expected_ship_date` | `tranId`, `tranDate`, `shipDate` |
| `notes`, `ship_to_address`, `bill_to_address`, `custom_fields` | `memo`, `shippingAddress`, `billingAddress`, `custbody_*` |
| `line_items` | Edit a line (send `line_item_id` and the changed fields), close a line (`line_item_id` with `close: true`), or add a line (omit `line_item_id`) |

### Cancel sales order

NetSuite has no cancel verb; cancellation closes every open line, which moves the order to closed.

### Create sales order shipment

| Trackstar field | NetSuite target |
| :--- | :--- |
| `shipped_date` | `tranDate` (date only) |
| `location_id`, `notes` | `location`, `memo` |
| `packages` | Tracking number and weight per package |
| `ship_to_address` | `shippingAddress` |
| `line_items` | Fulfilled lines with quantity; for lot- or bin-tracked items, the lot and bin per line. Lots and bins may be given by id or by name |
| `custom_fields` | `custbody_*` |

### Create purchase order

| Trackstar field | Required | NetSuite target |
| :--- | :---: | :--- |
| `vendor_id` | Yes | `entity` |
| `line_items` | Yes | Line items: `item`, `quantity`, `rate` (from `unit_price`), `location` |
| `employee_id` | No | `employee` (requestor) |
| `reference_id`, `order_number` | No | `externalId`, `tranId` |
| `order_date`, `expected_arrival_date` | No | `tranDate`, `dueDate` (date only) |
| `location_id`, `notes` | No | `location`, `memo` |
| `ship_to_address`, `bill_to_address`, `custom_fields` | No | `shippingAddress`, `billingAddress`, `custbody_*` |

On multi-subsidiary accounts, the subsidiary is set automatically from the vendor.

### Update purchase order

Follows the same pattern as updating a sales order: the vendor cannot be changed after create; header fields, addresses, and custom fields map as on create; and `line_items` supports editing, closing, or adding a line.

### Cancel purchase order

Closes every open line, the same way as cancelling a sales order.

### Create purchase order receipt

| Trackstar field | NetSuite target |
| :--- | :--- |
| `received_date` | `tranDate` (date only) |
| `location_id`, `notes` | `location`, `memo` |
| `line_items` | Received lines with quantity; for lot-tracked items, the lot per line |
| `custom_fields` | `custbody_*` |

## Behaviors and notes

- **Subsidiary auto-lookup.** On order and purchase-order create, the subsidiary is looked up from the customer or vendor so the request is well-formed on multi-subsidiary accounts. No subsidiary input is required.
- **Immutable entity on update.** The customer on a sales order and the vendor on a purchase order cannot be changed after create.
- **Line replace on update.** Order and purchase-order updates re-send every existing line, so unchanged lines are preserved and a partial line list will not drop lines.
- **Cancel closes lines.** Cancellation closes all open lines; NetSuite has no separate cancel verb.
- **Rate limits.** NetSuite governs API concurrency at the account level by service tier. Trackstar backs off automatically on throttling and supports per-flow sync frequencies to stay within limits.
- **Custom-field validation on write.** Unknown custom-field keys are rejected before the request, since NetSuite silently drops undeclared keys.
