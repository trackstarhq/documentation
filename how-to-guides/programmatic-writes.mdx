The Trackstar API enables you to write data into your end users' connected accounts.

Unlike reads, writes don't involve [syncing](/how-to-guides/syncing-data): when you perform a write operation (such as creating or updating a resource via `POST` or `PUT`), Trackstar forwards that request directly to the underlying integration in real time. We respond immediately with the success or error status from the integration, including any error messages or validation feedback provided by the integration itself. This ensures transparency and helps with rapid debugging and resolution when issues arise.

We have done the heavy lifting to unify the `body` of each action across integrations, so you can write data in a consistent way across all of them. For each resource, we call this the "Base Schema". See the [Create Order Base Schema](/api-reference/wms-api/orders/post#base-schema) as an example.

The required and optional fields may vary depending on the integration you are writing to. Additionally, some integrations may require a field that is unique to them. To handle these cases, we have also included each integration's schema in the reference. See [Extensiv's Create Order Schema](/api-reference/wms-api/orders/post#extensiv-3-pl-central) for an example.

On the API side, we have created an endpoint that will return the required and optional fields for a given integration.

## Example Create Return Request

Based on the response from the `/write-info` endpoint, the required and optional fields to create an order in the `Some WMS` integration are as follows:

| Field | Description | Type | Required |
| --- | --- | --- | --- |
| order\_id | The order ID associated with the return | string | Yes |
| warehouse\_id | The warehouse ID | string | No |
| line\_items | The line items | array | Yes |
| line\_items.sku | The SKU of the line item | string | Yes |
| line\_items.expected\_quantity | The expected quantity of the line item | number | Yes |
| line\_items.return\_cause | The reason for the line item's return | object | No |
| line\_items.return\_cause.code | The reason code for the line item's return. The values in this field are different for different connections - for this connection they are "1", "13", or "3" | string | Yes |
| line\_items.return\_cause.return\_reason | The reason description for the line item's return. The values in this field are different for different connections - for this connection they are "damaged", "wrong size", or "no longer needed" | string | No |
| return\_number | The RMA number | string | Yes |
| tracking\_number | The tracking number | string | No |
| tracking\_url | The tracking URL | string | No |
| trackstar\_tags | The [Trackstar Tags](/how-to-guides/trackstar-tags) | array | No |

Let's send in all of the fields for this request:

```bash
curl -X POST https://production.trackstarhq.com/wms/returns \
  -H "x-trackstar-api-key: <x-trackstar-api-key>" \
  -H "x-trackstar-access-token: <x-trackstar-access-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "order_id": "1234",
    "warehouse_id": "warehouse_1",
    "line_items": [
      {
        "sku": "123",
        "expected_quantity": 2,
        "return_cause": {
	  "code": "1",
	  "return_reason": "damaged"
	}
      }
    ],
    "return_number": "rma_456",
    "tracking_number": "tracking_abc",
    "tracking_url": "https://fedex.com/tracking_abc",
    "trackstar_tags": ["tag1"]
  }'
```

And that's it! You have successfully created an order in your end user's connected system.

## Non Nullable Fields

All fields in the write body are **non-nullable**. You cannot send a `null` / `"none"` / empty string for any field. This is because `null`s are ambiguous: they could mean you want the field blank on purpose, or maybe you're just using a default. The underlying systems also disagree on what a `null` should do (some clear the field, some reject the request, some ignore it). Rather than guess and risk writing data you didn't intend, we reject the request up front. If you don't mean to set a field, leave it out of the body entirely.

For example, `tracking_number` and `tracking_url` are optional fields. Sending in the following request will result in a 422 error response:

```bash
  curl -X POST https://production.trackstarhq.com/wms/returns \
  -H "x-trackstar-api-key: <x-trackstar-api-key>" \
  -H "x-trackstar-access-token: <x-trackstar-access-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "order_id": "1234",
    "warehouse_id": "warehouse_1",
    "line_items": [
      {
        "sku": "123",
        "expected_quantity": 2,
        "return_cause": {
	  "code": "1",
	  "return_reason": "damaged"
	}
      }
    ],
    "return_number": "rma_456",
    "tracking_number": "",
    "tracking_url": null
  }'
```

Instead, you should omit the fields from the request like so:

```bash
  curl -X POST https://production.trackstarhq.com/wms/returns \
  -H "x-trackstar-api-key: <x-trackstar-api-key>" \
  -H "x-trackstar-access-token: <x-trackstar-access-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "order_id": "1234",
    "warehouse_id": "warehouse_1",
    "line_items": [
      {
        "sku": "123",
        "expected_quantity": 2,
        "return_cause": {
	  "code": "1",
	  "return_reason": "damaged"
	}
      }
    ],
    "return_number": "rma_456"
  }'
```

## Safe Retries with Idempotency Keys

When you write to the integration, it happens right away. If the network has a problem or times out, you might not know if your write actually went through. If you try again without checking, the write could be applied twice in the connected system, such as a duplicate order or the same file attached again.

To make retrying safe, send an `Idempotency-Key` header with your write. Use a unique value for each write, like a UUID (up to 255 characters). If you retry with the same key, we'll give you the response from the first request instead of sending it to the integration again.

```bash
curl -X POST https://production.trackstarhq.com/wms/returns \
  -H "x-trackstar-api-key: <x-trackstar-api-key>" \
  -H "x-trackstar-access-token: <x-trackstar-access-token>" \
  -H "Idempotency-Key: 9f1c2b1e-6d4a-4c1c-9a8e-2b7e3c5d1f00" \
  -H "Content-Type: application/json" \
  -d '{
    "order_id": "1234",
    "line_items": [
      {
        "sku": "123",
        "expected_quantity": 2
      }
    ],
    "return_number": "rma_456"
  }'
```

The response to a retried request with the same key depends on what happened to the first request:

| First request | Retry with the same key |
| --- | --- |
| Succeeded | You get the first request's response, with an `Idempotent-Replayed: true` header. The write is not sent to the integration again. |
| Failed | The key gets released. Your retry is sent to the integration as a new write. |
| Still in progress | You get a `409`. Wait for the first request to finish, then try again. If it hasn't finished after 15 minutes, your retry is sent as a new write. |
| Sent to a different endpoint or with a different body | You get a `400`. A key belongs to one exact request. |

A few more things to know:

- Keys expire 24 hours after the first request. After that, the same key acts like a new one.
- Keys are tied to a connection. Using the same key on two different connections counts as two separate keys.
- A retry still counts as the same request if its body lists the fields in a different order or uses different spacing. Reordering the items inside a list, such as `line_items`, **does** make it a different request.
- Every write endpoint accepts this header, including cancels and batch writes. [Passthrough requests](/how-to-guides/passthrough-requests) don't.

<Warning>
  A key only replays a write that worked. If we return an error (5xx), a retry with the same key is sent to the integration again. In rare cases, the integration saves the record before the error happens. For example, it might accept an order but time out before it confirms the order. A retry then creates a duplicate unless the integration rejects duplicates itself, such as when it rejects a repeated order number.
</Warning>

## Don't See a Field You Need?

If the field is part of Trackstar's schema (think `order_number`, `carrier_name`, `expected_arrival_date` etc) then reach out to us and we'll gladly expose it for you if the integration allows.
